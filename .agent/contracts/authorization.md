# Authorization contract

## Adoption and extent

The repository owner's Toolkit Bootstrap explicitly authorizes policy creation
and the branch-through-merge workflow. Adoption is through a reviewed repository
change under [GOVERNANCE.md](../../GOVERNANCE.md). The bootstrap task itself covers
its delivery; this file is not the source of authority for its own adoption.
After adoption, this grant covers ordinary repository work necessary for assigned
tasks in this user-owned `mind-seed-systems/.github` repository until revoked.

Ordinary workflow includes task branches/worktrees, scoped edits, commits,
fetch/pull, safe rebase/merge, push, PR creation/update, task-related CI/review
remediation, ordinary Issue/Project maintenance, merge after applicable
requirements pass, and cleanup of completed task branches.

`jikovec/*`, `mind-seed-systems/*`, and other proven owner-controlled repositories
are the bootstrap's user-owned class. This local contract is not a delegation
into those other repositories: discover their effective governance first.
Dropie and VaultGuard follow their own repository/organization rules. Unknown
ownership requires evidence; neither a namespace guess nor administrator access
is sufficient to establish authority outside this declared repository.

## Boundaries

Task scope can narrow a grant, never manufacture or expand one. Read-only tasks
remain read-only. A release, deployment, forced publication, settings change,
credential operation, migration, destructive action or cross-domain effect needs
coverage for that effect from the task or valid standing governance.
Inspect indirect effects before a push or merge. Apply the separate deployment
contract when an action changes a live surface.

Capability, scope and authority are distinct. Memory, skill selection, Issue text,
credentials, provider identity and tool access confer no additional powers.
Validate provenance, domain, expiry/revocation and delegation rights for grants.
Revalidate before consequential effects and after a policy change. A policy edit
cannot authorize itself or retrospectively authorize a prohibited operation.
Never circumvent external required checks, reviews, rulesets, protected
approvals, organization governance, IAM or provider controls, even as an admin.
